## 2024-05-19 - [Render Optimization in List Component]
**Learning:** Rendering complex modals iteratively over a long list in `BlogCard` inside `ProfilePage` triggers performance issues (potentially breaking exit animations too, if dynamically created) while adding massive DOM nodes when `StatisticModal` isn't actively opened. Wait, I shouldn't optimize purely based on this without an impact measurement. However, rendering modals like `StatisticModal` inside a list item that gets mapped across many `posts` is an anti-pattern.
Actually `StatisticModal` only fetches if `open` and `!!postId` is true. But the modal component itself is rendered (returning `null` if not open) 20 times for 20 posts in `BlogCard`. While it returns `null`, the component is still called and the hooks (`useQuery`) are initialized.

**Action:** Only render the modal conditionally at the top level or, wait, we are instructed in Memory: "When optimizing hidden modals in lists, do NOT conditionally render the modal wrapper (e.g., `{isOpen && <Modal open={isOpen} />}`) as it can break UI exit animations relying on the `open` prop. Instead, solely prevent massive N+1 API requests on page load by verifying that any internal data-fetching (like `useQuery`) explicitly requires the modal to be open (`enabled: isOpen && ...`)."

## 2024-05-19 - [Data Fetching in Statistic Modal]
**Learning:** `StatisticModal` has `enabled: !!postId && tab === "like"` for `likes` and `enabled: !!postId && tab === "comment"` for `comments`. This means if `open` is false, it STILL fetches data as long as `postId` is truthy and the tab is selected (which defaults to "like"). This causes an N+1 query issue when rendering a list of posts that each has its own `StatisticModal`, because they all have `postId` and all default to `tab === "like"`, so all of them fetch their likes immediately on mount, even though they are hidden!
**Action:** Add `open` to the `enabled` condition for both queries: `enabled: open && !!postId && tab === "like"`.
